## Реализация на Go

В данном примере:

- `LegacyPrinter` — существующий интерфейс (старый принтер).
- `ModernPrinter` — целевой интерфейс, который ожидает клиент.
- `PrinterAdapter` — адаптер, который реализует `ModernPrinter`, но делегирует вызовы внутреннему объекту `LegacyPrinter`.

### Код с описанием

```go
package main
import "fmt"
```

1. Создаем существующий интерфейс (тот, что будем адаптировать)
   
```go
type LegacyPrinter interface {
	PrintLegacy(text string) string
}
```

3. Реализация старого интерфейса
   
```go
type OldPrinter struct{}

func (p *OldPrinter) PrintLegacy(text string) string {
	return text + " - хорошо забытое старое"
}
```

4. Целевой интерфейс, который ожидает клиент

```go
type ModernPrinter interface {
	PrintModern(text string) string
}
```

5. Тот самый адаптер, который преобразует LegacyPrinter в ModernPrinter

```go
type PrinterAdapter struct {
	LegacyPrinter LegacyPrinter
}
```

6. Реализация целевого интерфейса через адаптер. Реализуем через делегирование вызова к встроенному объекту

```go
func (adapter *PrinterAdapter) PrintModern(text string) string {
	return adapter.LegacyPrinter.PrintLegacy(text)
}
```
**Пример использования в *main***

```go
func main() {
	oldPrinter := &OldPrinter{}
	adapter := &PrinterAdapter{
		LegacyPrinter: oldPrinter,
	}
	var modernPrinter ModernPrinter = adapter
	result := modernPrinter.PrintModern("Все новое")
	fmt.Println(result)
}
```
### Запуск программы 

```bash
go run L1.21.go
```
**Результат вывода**
```
Все новое - хорошо забытое старое
```

## Применимость паттерна

**Когда нужно использовать:**

- Интеграция сторонних библиотек или legacy-кода с новой системой.
- Поддержка нескольких версий API без изменения клиентского кода.
- Упрощение тестирования через моки/заглушки.

---

## Плюсы

- **Гибкость**: позволяет работать с несовместимыми интерфейсами.
- **Разделение ответственности**: клиент не зависит от реализации адаптируемого класса.
- **Простота расширения**: можно добавлять новые адаптеры без изменения существующего кода.

---

## Минусы

- **Увеличение сложности**: добавляет дополнительный уровень абстракции.
- **Возможные потери производительности**: из-за дополнительного уровня вызовов.
- **Опасность “адаптерной лавины”**: если слишком много адаптеров, система становится трудно поддерживаемой.

---

## Реальные примеры использования

1. **Интеграция сторонних API**  
   Например, адаптер для работы с разными платежными шлюзами (Stripe, PayPal, YooKassa), предоставляя единый интерфейс.

2. **Работа с базами данных**  
   Адаптер для SQL и NoSQL БД, чтобы клиентский код мог работать с любым хранилищем через общий интерфейс.

3. **GUI фреймворки**  
   Адаптер для разных платформ (Windows, macOS, Linux) при работе с графическими элементами.

4. **Логгеры**  
   Адаптер для логгеров сторонних библиотек (например, Zap, Logrus, stdlog) под единый интерфейс.
